# InnerCore — Ядро: образы, символы и RAG

**Статус:** Аудит + архитектурная карта (живой документ)
**Дата:** 2026-06-15
**Область:** `backend/` (rag_service, map_service, embedding_service, tasks), `llm_service/`, `frontend/` (Карта снов, «Что возвращается»)

> Это **ядро продукта**. На извлечении образов из снов, их нормализации, накоплении и связывании (RAG) строится вся суть психоанализа в InnerCore: анализ сна, Карта снов, «повторяющиеся образы», динамика во времени. Качество этого слоя = качество продукта. Документ фиксирует, как оно устроено сейчас, где именно ломается (со ссылками на строки и замерами) и в каком порядке чинить.

---

## 1. Что вообще происходит (поток данных)

```
ЗАПИСЬ
  голос → POST /audio/transcriptions (api/audio.py)
            → transcription_service: split_audio (сегменты по 15с, pydub)
              → CometAPI Whisper параллельно (3 одновременно, 3 ретрая) → склейка
  текст → POST /dreams (dream_service.create_dream) → Dream

АНАЛИЗ (Celery: tasks._analyze_dream_async)
  Dream.content
    ├─ ПУТЬ A (rule-based, rag_service):
    │    chunk_dream_text  → DreamChunk (+ chunk-эмбеддинг)
    │    extract_symbols   → DreamSymbol      ← частотность токенов
    │
    └─ ПУТЬ B (LLM, llm_service /analyze):
         symbol_entities   → DreamSymbolEntity ← образы для Карты
            чистка №1: llm_service/main.py:_normalize_symbol_entities
            чистка №2: rag_service.py:_sanitize_symbol_entities
            если пусто → _fallback_symbol_entities (= снова ПУТЬ A)

ПОТРЕБИТЕЛИ
  Карта снов (map_service)         ← DreamSymbolEntity (ПУТЬ B)
  «Recurring symbols» в retrieval  ← DreamSymbol (ПУТЬ A)
  «Что возвращается» (web)         ← НИЧЕГО из бэка, считает на клиенте (!)
```

**Ключевой факт №1:** из одного текста сна образы извлекаются **двумя независимыми системами** (A и B), которые дают **разные наборы** и питают **разных потребителей**. Это не дублирование ради надёжности — это рассинхрон.

**Ключевой факт №2:** биллинг (FREE = запись без лимита, **2 анализа в неделю**) означает, что у типичного пользователя **большинство снов не анализированы**. Значит ПУТЬ B для них не запускался, и всё, что зависит от `DreamSymbolEntity`, для этих снов строится из аварийного частотного фолбэка.

## 2. Модель данных (`backend/models/rag.py`)

| Таблица | Что хранит | Кто пишет | Кто читает |
|---|---|---|---|
| `dream_chunks` | куски текста ≤320 симв. + эмбеддинг чанка | ПУТЬ A | retrieval, Карта |
| `dream_symbols` | нормализованный токен (частотный) | ПУТЬ A | retrieval (symbol_overlap, recurring) |
| `dream_archetypes` | дельта архетипа на сон | LLM `archetypes_delta` | retrieval, Карта (цвет кластера) |
| `dream_symbol_entities` | образ: `canonical_name`, `display_label`, `entity_type`, `weight`, `related_archetypes` | ПУТЬ B (или фолбэк A) | **Карта снов** |

Эмбеддинги хранятся как JSON-текст в Postgres (`embedding_text`); **pgvector нет**, косинус считается в Python (`embedding_service.cosine_similarity`). Провайдер — CometAPI `text-embedding-3-small`.

## 3. Подтверждённые дефекты

Каждый — со ссылкой на строки и, где возможно, с замером. Делятся на **видимые баги** (репортил пользователь) и **корневые причины** под ними.

### 3.1 Видимый баг — «Что возвращается»: бредовые символы

**Симптом:** карточка показывает `Есть 9, Будто 9, Какие-то 8, Какой-то 7, Потом 7, Жена 6`.

**Корень:** `frontend/src/pages/TodayPage.tsx:23-41` (`extractMotifs`) считает частоту слов **на клиенте**, со своим списком стоп-слов (~40 слов: `и, в, на, не, я…`), где нет `есть / будто / какие-то / какой-то / потом / жена`. Бэкенд-пайплайн образов **не используется вообще** — ни LLM-образы, ни лемматизация, ни канонические имена.

- Поэтому `Будто`/`Потом` проходят, хотя в бэкенде они в стоп-листе — этот стоп-лист тут ни при чём.
- `Жена` — реальный повторяющийся образ, но показан сырым словом, без концепта.

**Почему так:** на бэке **нет эндпоинта** «топ повторяющихся образов». `stats_service.get_user_stats` отдаёт только `archetypes_top`. Веб считает сам от безысходности.

**Фикс:** добавить бэкенд-эндпоинт recurring-symbols поверх `DreamSymbolEntity` (чистые канонические имена, дедуп, лемма) и кормить карточку им.

### 3.2 Видимый баг — «Связанные символы» пустые (• • • • •)

**Симптом:** в карточке образа блок «Связанные символы» = 5 пустых буллетов.

**Корень — рассинхрон контракта**, данные при этом непустые (иначе блок был бы скрыт условием `length > 0`):

- Бэк: `backend/schemas/map.py:76` → `related_symbols: list[str]` — отдаёт **строки**.
- Фронт: `frontend/src/lib/types.ts:125` ждёт `{ id, symbol_name, display_label }[]`, рендерит `{s.display_label || s.symbol_name}` (`MapPage.tsx:289-291`).
- На строке оба поля = `undefined` → `• ` без текста, 5 штук.

Та же ручка читается в Flutter (`client/lib/models/dream_map.dart:215`) — вероятно, сломано и на мобиле.

Дополнительно: фильтр в `map_service.get_map_symbol_detail:399` отбрасывает однословные лейблы (`len(label.split()) < 2`), сужая список ещё до рендера.

**Фикс:** свести контракт. Предпочтительно — бэк отдаёт объекты `{id, symbol_name, display_label}` (даёт ключ и кликабельность), фронт уже к этому готов.

### 3.3 Видимый баг — Карта: изолированные по-сновые кластеры, нет пересечения смыслов

**Симптом:** точки слиты в очень плотные группы с большими зазорами; каждая группа = один сон; дисперсии и пересечения смыслов нет → карта не несёт информации.

**Корень:** в `map_service._load_symbol_runtimes:560-561` эмбеддинг **узла-символа = среднее эмбеддингов чанков**, где он встретился (т.е. фактически текст сна). Эмбеддинг самого концепта (`request_embedding(display_label)`) — только фолбэк при отсутствии чанков (строка 564).

Цепочка следствий:
1. Все символы одного сна наследуют ~один чанк-эмбеддинг → схлопываются в точку.
2. Без лемматизации символы между снами почти не объединяются (каждый встречается 1 раз) → узел = один сон.
3. UMAP (`metric=cosine`) + DBSCAN с `eps` = 22-й перцентиль попарных расстояний (`_cluster_points:750-752`) на бимодальном распределении (внутри сна крошечные расстояния, между снами огромные) → **кластер на каждый сон**.

Итог: карта «по облаку на сон», а не «по региону на смысл».

**Фикс:** эмбеддить **сам образ** (`canonical_name`/`display_label`, опционально с лёгкой добавкой контекста), а не сырой чанк. Тогда `озеро` рядом с `море`/`река` независимо от сна; фигуры `мама`/`жена` группируются; разные по смыслу образы одного сна расходятся.

### 3.4 Корень — лемматизации фактически нет

`_normalize_symbol` (`rag_service.py:163`) = словарь `_SYMBOL_ALIASES` на ~30 ручных записей. Всё остальное не сводится к канонической форме. Замер (точная реплика `extract_symbols`, см. Приложение A):

```
лес      <- ['лес']
лесом    <- ['лесом']     ← НЕ слито с «лес»
лесами   <- ['лесами']    ← НЕ слито
мама     ≠  мать  ≠  матери        ← три разных символа
машина   ≠  машиной
дорога   ≠  дороге  ≠  дорогой
```

Весь смысл «повторяющихся образов» — заметить возврат образа. Но `лес` сегодня и `лесом` завтра — для системы разные символы. Рекуррентность ловится только для слов из таблицы алиасов. На Карте это даёт узлы-дубли одного образа.

**Фикс:** настоящая лемматизация — `pymorphy3` для RU + лёгкий стемминг EN — вместо таблицы алиасов.

### 3.5 Корень — нет POS-фильтра → глаголы/прилагательные становятся «образами»

`extract_symbols` фильтрует только короткий `_STOPWORDS`. Замер на типичных снах:

| Сон | Что названо «образами» |
|---|---|
| Погоня в лесу | `дом, бежал, тёмный, мной, кто, гнался, деревья` |
| Вода и зеркало | `вода, снилось, стою, море, была, чёрная, отражалась, луна` |
| Разговорный | `ехали, короче, такой, сон, типа, еду, машина, кстати` |

`бежал, гнался, стою, отражалась, тёмный, чёрная` — глаголы/прилагательные, не образы. `_is_symbol_candidate` на Карте режет только список `_GENERIC_SYMBOLS`, а их там нет → они выживают как узлы с подписью `образ бежал`.

**Фикс:** `pymorphy3` даёт часть речи бесплатно — оставлять преимущественно существительные (+ именные группы).

### 3.6 Корень — частотный фолбэк отравляет Карту для неанализированных снов

`map_service._load_chunk_runtimes:609-616`: для сна **без чанков** вызывается `rebuild_dream_memory(db, dream, user_id)` **без `symbol_entities`** → `_fallback_symbol_entities` (частотность) пишет в `DreamSymbolEntity`. С учётом биллинга (см. §1) это **большинство снов** → большая часть узлов Карты у типичного юзера сделана частотным мусором, а не LLM.

**Фикс:** убрать частотный фолбэк с Карты — либо дешёвый отдельный extract-only LLM-вызов при первом построении Карты, либо не показывать неанализированные сны как узлы.

### 3.7 Корень — три расходящихся списка стоп-слов/нормализации

- `rag_service._ENTITY_STOPWORDS` (есть `эльфов/феи`)
- `llm_service/main.py:_ENTITY_STOPWORDS` (свой `_normalize_token`, **без** алиасов)
- `map_service._GENERIC_SYMBOLS` + `_LABEL_STOPWORDS` (есть `трекинг/gps`)

Токен, вычищенный на одном этапе, всплывает на другом. `_normalize_symbol` (алиасы) живёт только в `rag_service`; `llm_service` нормализует `canonical_name` без алиас-фолдинга → нормализация на границе сервисов несогласована.

**Фикс:** единый модуль нормализации/стоп-слов, импортируемый всеми тремя местами.

### 3.8 Корень — RAG-контекст считается, но в первичный анализ не доходит

`tasks._analyze_dream_async`: `build_llm_context(..., include_retrieval=False)` строится (стр. 126) и **никуда не передаётся**; `rebuild_dream_memory` возвращает retrieval, но результат игнорируется. Первичный анализ видит только текст одного сна + `user.md`. Полный retrieval-блок («recurring symbols from memory», связанные чанки) доходит до LLM **только в follow-up чате** (`build_llm_context` с дефолтным `include_retrieval=True`). То есть связи между снами в первичном анализе сейчас держатся исключительно на `user.md`.

**Фикс (отдельный трек):** прокинуть retrieval в первичный анализ; убрать мёртвый вызов `build_llm_context` в analyze-пути.

### 3.9 Артефакт подписей `образ X` / `мотив X`

Правило «≥2 слов, иначе префикс» (`rag_service:195-198`, `map_service:558/905`) выдаёт `образ дом`, `мотив машина` всякий раз, когда канон одно слово. Видимый на Карте мусор в подписях.

**2026-06-15 — РАЗВОРОТ #4: pymorphy отвергнут в пользу группировки на эмбеддингах.**
Аргумент владельца: «работаем с LLM — зачем жёсткие словари?». Разделили две задачи: **извлечение** (LLM — он уже это делает в `symbol_entities`) и **группировку синонимов/форм** (детерминизм/эмбеддинги, т.к. независимые stateless-вызовы LLM не дают консистентный канонический ключ через весь архив).
- **Убран** `pymorphy3` (+ requirements): лемматизации и POS-фильтра больше нет. `text_normalization` упрощён до lowercase-нормализации + стоп-слов + `clean_label` (бэкап-фолбэк/overlap, низкие ставки).
