# Заметки: снижение потребления памяти sleep-бэкенда

> Контекст для рефакторинга sleep-проекта. Возвращаемся к этому позже.
> Наш yt-бот памяти ест мало (~260 МБ) и здесь не проблема — это про sleep.

## Текущая картина (prod, 31.76.8.29, 3.9ГБ RAM)

`sleep-prod/backend` — главный потребитель памяти: **~1.2 ГБ**
- uvicorn (основное приложение): ~374 МБ
- 3 celery-воркера: ~845 МБ суммарно (~244–357 МБ каждый)

Остальное:
- прокси-стек (mita / caddy / xray / sing-box): ~230 МБ
- наш yt-бот + сервер: ~260 МБ

Реальная нагрузка пользователей сейчас мала, а память резервируется как для сервиса с сотнями активных онлайн-пользователей.

## Почему celery ест так много

- Каждый воркер — **отдельный Python-процесс** со своей копией интерпретатора и библиотек в RAM (память не разделяется между процессами из-за GIL в CPython).
- По умолчанию каждый воркер поднимает несколько дочерних процессов (`--concurrency`), что множит потребление.
- Итого: `процесс × интерпретатор × зависимости` = много RAM даже при холостой работе.

## Предложения по снижению

### 1. Autoscale (рекомендовано)
Сократить рантайм-минимум и поднимать воркеры только при наплыве задач:
```bash
celery -A app worker --autoscale=<max>,<min>
# пример для редких коротких задач:
celery -A app worker --autoscale=2,1
```
Воркер держит базовый минимум (min), при росте очереди поднимает до max, простаивающие закрывает.

### 2. Ограничить память дочернего процесса
Дёшево перезапускать процесс, съевший лимит (не даёт утечкам накапливаться):
```bash
celery -A app worker --maxmemoryperchild=200000   # 200 МБ
```

### 3. Сократить число воркеров и concurrency
Если задачи короткие и редкие — `--concurrency=1` и 1–2 воркера вместо 3×ии больших concurrency. Может срезать сотни МБ при почти нулевой потере производительности на лёгкой нагрузке.

### 4. Прочее
- При необходимости выносить тяжёлые задачи в отдельный асинхронный обработчик (asyncio / Dramatiq) — но для текущего профиля нагрузки это избыточно.
- Проверить, нет ли утечек памяти (нужен медленный тест на рост RSS воркеров со временем).

## Что мы здесь НЕ делаем

- К конфигу и systemd-юнитам `sleep-prod/backend` НЕ прикасаемся — это чужой автопарк.
- Изменения внедряем только при рефакторинге самого sleep-проекта.
